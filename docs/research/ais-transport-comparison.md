## Fintraffic: сравнение в одном окне

Две подписки по 30 секунд с REST-снимком в начале и в конце каждой. В MQTT-распределение входят отдельные сообщения, в REST — записи снимка. Возраст измеряется относительно времени, указанного поставщиком, по часам клиента. Это разные выборки; непосредственное сравнение p95 не измеряет ускорение доставки. Для проверки перекрытия сопоставлены одни и те же MMSI, без сохранения идентификаторов.

| Старт UTC | MQTT: сообщений / разных MMSI | MQTT возраст p50 / p95 | REST после окна: записей, из них старше часа | Общие MMSI с финальным REST: у скольких время MQTT новее |
|---|---:|---:|---:|---:|
| 18:32:11 | 934 / 318 | 0,509 / 0,970 с | 787, из них 204 | 318 из 318 |
| 18:33:35 | 926 / 297 | 0,534 / 0,972 с | 784, из них 201 | 297 из 297 |

MQTT начал передавать обновления сразу после подписки. Брокер принял варианты `vessels-v2/+/location` и `vessels-v2/+/locations` на QoS 0, но все полученные сообщения пришли на **`/location`**. Оба варианта фигурируют на [официальной странице](https://www.digitraffic.fi/en/marine-traffic/); ноль сообщений на втором за короткое окно не доказывает, что топик никогда не используется. В полученном JSON время было в поле `time`, Unix-секунды; REST возвращал `timestampExternal` в миллисекундах по [OpenAPI](https://meri.digitraffic.fi/swagger/openapi.json). Сравнение выполнено с точностью до секунды по самому новому MQTT времени данного MMSI. Не доказано, что эти поля описывают идентичный этап обработки у поставщика.

В REST-профиле на час раньше (17:35 UTC) было 196 из 796 записей старше часа; в последних снимках в 18:32–18:34 UTC — 201–205 из 784–788. Это два близких вечерних периода одного дня. Полного дневного профиля, частоты обновлений на конкретном судне, гарантий доставки, стабильности reconnect и полноты региона пока нет. Практический вывод: REST подходит для начального снимка и сверки состояния, MQTT — кандидат для обновлений между снимками.

## Kystverket: свежесть ответа и время

| Старт UTC | GeoJSON features | Разных девятизначных ключей MMSI | Возраст p50 / p95 | Старше 5 мин | Время не разобрано |
|---|---:|---:|---:|---:|---:|
| 18:32:11 | 3 653 | 3 639 | 13,52 / 186,52 с | 78 | 17 |
| 18:33:34 | 3 649 | 3 636 | 13,97 / 185,97 с | 61 | 0 |

Первый запуск использовал Python 3.9: ISO-время с 4–5 знаками дробной секунды оказалось неподдержанным в `fromisoformat`. Промежуточный GET подтвердил обе формы. Во второй пробе дробная часть нормализована к микросекундам, и разобрались все 3 649 строк. `date_time_utc` был без смещения; UTC принят по названию поля и описанию интерфейса. Формат и валидность MMSI считались отдельно: 7 строк второй пробы не имели ключа из девяти цифр, ещё 6 повторяли такой ключ. Это не вывод об идентичности корпусов. Источник: [Kystdatahuset OpenAPI](https://kystdatahuset.kystverket.no/ws/swagger/v1/swagger.json).

В историческом API повторены три пятиминутных окна: вернулось **2, 10 и 35 строк** по 12 полей. Внутри JSON строки представлены позиционными массивами. Проба с предположением, что это объекты, сначала завершилась ошибкой разбора при HTTP 200. Для анализа сырых разрывов этот API ограничен: он отдаёт производные вершины и использует фильтр скорости.
