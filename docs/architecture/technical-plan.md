# Технический план — последовательность проверяемых этапов

Это план проектирования и будущей разработки; авторизация на реализацию frontend/backend пока отсутствует. Решения о стеке — предложения. Зависимые этапы начинаются после результатов предыдущих.

1. **Источник и права.** Для каждого кандидата сохранить URL, дату проверки, способ доступа, JSON/NMEA sample, лимиты, покрытие, хранение, атрибуцию. Выход: таблица разрешённых сценариев и ошибки повторяемых проб. Базовый результат уже в [API probes](../research/api-probes.md).
2. **Нормализованный контракт.** Описать source adapter и sample JSON для позиции, статических данных, качества и provenance. Проверить координаты, единицы и время на нескольких источниках. Выход: schema + mapping с неизвестными значениями.
3. **Identity и evidence.** Описать жизненный цикл MMSI/IMO/имён, правила сопоставления и ручной проверки. Выход: примеры конфликтов и объяснимые claim записи.
4. **История и current projection.** Проверить дедупликацию, late arrival, перезапуски, retention и объём данных на ограниченной выборке. Выход: доказанная семантика latest и оценка ресурса.
5. **Детекторы.** Начать с объяснимых правил; определить параметры и отрицательные примеры. Выход: воспроизводимые события и анализ ложных срабатываний.
6. **Картографический контракт.** Проверить bbox, антимеридиан, классификацию свежести и источник покрытия. Выход: JSON схемы для карты без UI реализации.
7. **После отдельного решения о реализации.** Выбрать БД, API и картографический стек по замерам; написать независимые планы для ingest, query и UI. Для каждого этапа обязательны fixture, проверка контрактов и source compliance.

Порядок источников для проб: Digitraffic подтверждён реальным REST JSON; AISstream после ключа и проверки условий; Kystverket после проверки маршрута; GFW/OpenSanctions как независимые evidence источники. Глобальную полноту не обещать. Результат каждого этапа — документ с входами, выходами, ограничениями и решением продолжать/пересмотреть подход.
