# System design v0.1 — от AIS до карты

**Draft.** [ТЗ](technical-spec.md) · [ER и БД](database-design.md) · [План](technical-plan.md) · [Архитектурная схема](diagrams/architecture.html) · [Сверка снимка с потоком](diagrams/reconcile.html).

## Выбор архитектуры

Рекомендация: два процесса одного Python-проекта (сбор и чтение API), одна PostgreSQL/PostGIS и лёгкий браузерный клиент. Сборщик — единственный писатель. API читает текущие позиции и здоровье. Браузер опрашивает API, пока отдельные потоки на клиента не нужны. Предлагаемый стек: Python, Paho MQTT, FastAPI, psycopg, PostgreSQL/PostGIS, MapLibre GL JS и TypeScript. Версии зафиксировать при старте. Официальная справка: [геометрия bbox](https://postgis.net/docs/ST_MakeEnvelope.html), [границы транзакций](https://www.postgresql.org/docs/current/transaction-iso.html).

Вариант с in-memory проекцией годится для одноразового прототипа, но теряет состояние при рестарте. SQLite проще локально, PostgreSQL выбран для draft из-за пространственного индекса, единого транзакционного снимка и будущих пространственных запросов. Kafka, Redis, отдельная шина и WebSocket на клиент не нужны в v0.1. Срез проверяем локально, эксплуатационные роли остаются разделены.

| Модуль | Вход → выход | Ответственность |
|---|---|---|
| Fintraffic adapter | REST GeoJSON / MQTT JSON → канонический кандидат | Проверка формата; timestampExternal как мс, time как с; обработка лимитов, ошибок, TLS |
| Reconciler | Кандидат + текущее состояние → принять / игнорировать / конфликт | Версия времени, tie-break, защита от старого сообщения, поколение подключения |
| Position store | Пачка позиций + состояние соединения → атомарный commit | Ключ источника и MMSI; TTL; повторяемое чтение; наблюдаемость |
| Read API | Bbox или ключ → JSON + состояние источника | Валидация, ограничение результата, атрибуция, вычисленный возраст |
| Map | JSON → маркеры, панель наблюдения, информация о зоне | Показывает время и возраст; не делает внешних AIS-запросов |

## Порядок соединения и восстановления

1. Сборщик берёт PostgreSQL advisory lock на отдельном соединении, через которое пишет; потеря соединения отменяет сеанс записи. Новый сеанс получает новый epoch. Старые callbacks игнорируются. При старте уже сохранённые позиции доступны, состояние — degraded/starting.
2. TLS → MQTT CONNACK → SUBACK на `vessels-v2/+/location`. В очередь текущего epoch поступают сообщения, включая те, что приходят сразу после подписки. Retained не считается свежим push. Затем один REST GET. Предлагаемые буфер и лимиты: 10 000 сообщений или 8 МиБ, 15 с на REST, отдельный лимит 8 МиБ на сетевое и распакованное тело.
3. Снимок и отложенные сообщения нормализуются по одному контракту. После разбора снимка фиксируется порядковый номер хвоста очереди — watermark. Запись снимка и сообщений до watermark выполняется атомарно вместе с маркером успешной сверки; в момент переключения входные события продолжают идти через ту же очередь, без второго писателя. Сообщения после watermark обрабатываются обычными пачками после commit: бесконечное ожидание пустой очереди запрещено. Общий лимит охватывает очередь и сообщения в текущей неподтверждённой пачке. MQTT QoS 0 и REST не восстанавливают весь пропущенный поток. Пустой валидный снимок не удаляет наблюдения.
4. После сверки apply batches: до 250 сообщений или 500 мс ожидания, что раньше. Время записи в источнике определяет версию; время получения отвечает за диагностику. Запись для одного ключа не может перейти на более старую секунду [по правилам БД](database-design.md).
5. Disconnect, застой валидных сообщений >60 с, ошибка REST, исчерпание очереди или БД: degraded, остаётся последняя подтверждённая проекция. Закрыть неуспешное поколение, очистить его очередь, повторить соединение и сверку с jitter 2–60 с; на 429 уважать Retry-After. Таймеры и пороги — предложения. Поздний callback закрытого поколения не меняет подлинное состояние. Состояние API дополнительно становится degraded при просроченном heartbeat писателя.

Два канала описывают время записи поставщика с разной точностью. Сравнение в пределах секунды не устанавливает физический порядок записи. Политика tie-break в модели БД служит воспроизводимости; MQTT остаётся низколатентным каналом, а не гарантированно независимым наблюдением.

## Минимальный сетевой контракт

| Маршрут | Ответ |
|---|---|
| GET /v1/positions?west=&south=&east=&north= | `as_of` UTC, `source` с id, attribution, license_url, sync_state, last_mqtt_at, last_snapshot_at; `items`; `truncated`. 400 — неверный или неполный bbox, 503 — БД недоступна. Пустая выборка — 200. |
| GET /v1/positions/{source}/{mmsi} | Одна позиция с теми же полями, что в списке; 404 — нет сохранённой неистекшей записи. |

Позиция: `source_id`, строка `mmsi`, `lon`, `lat`, `provider_time`, `time_precision` (second/millisecond), `transport` (rest/mqtt), `received_at`, `age_seconds`, `stale`, `time_conflict`, `clock_skew`, nullable `sog_kn`, `cog_deg`, `heading_deg`. Координаты WGS84. Возраст = max(0, as_of − provider_time) в секундах; stale вычисляется по неокруглённому возрасту. Bbox конечный; west/east в [-180,180], south/north в [-90,90]; `south < north`, `west != east`; `west > east` — две области, объединение без повтора. Целый мир: -180,-90,180,90. Каноническая долгота в [-180,180); границы включены. Сначала определить тип интервала по исходным west/east, затем обработать шов: +180 включает каноническую точку -180, но не превращает обычный интервал в пересекающий шов. west=180,east=-180 отклоняется как нулевая ширина; west=-180,east=180 обозначает весь мир. Сортировка по provider_bucket DESC, source_id ASC, mmsi ASC, limit+1. API читает состояние и позиции из одного снимка БД, при ошибке обновления клиент сохраняет последнюю карту, явно помечает её устаревшей и показывает время последнего успешного ответа. Данные не выглядят свежими при остановке опроса.

Пример ответа списка (синтетические данные):

```json
{
  "as_of": "2026-11-14T18:00:04Z",
  "source": {
    "id": "fintraffic",
    "attribution": "Fintraffic / Digitraffic",
    "license_url": "https://creativecommons.org/licenses/by/4.0/",
    "sync_state": "live",
    "last_mqtt_at": "2026-11-14T18:00:02Z",
    "last_snapshot_at": "2026-11-14T18:00:01Z"
  },
  "items": [{
    "source_id": "fintraffic", "mmsi": "000000000", "lon": 25.1, "lat": 60.0,
    "provider_time": "2026-11-14T18:00:02Z", "time_precision": "second",
    "transport": "mqtt", "received_at": "2026-11-14T18:00:02.350Z",
    "age_seconds": 2, "stale": false, "time_conflict": false, "clock_skew": false,
    "sog_kn": 0, "cog_deg": null, "heading_deg": null
  }],
  "truncated": false
}
```

Состояние `live` означает успешную сверку текущего epoch и недавний валидный push; `syncing` — подготовку снимка; `starting` — ожидание первой сверки; `degraded` — сбой или истёкший heartbeat. Предлагается heartbeat раз в 5 с с отсечкой 15 с на чтении; при рестарте прежние диагностические отметки можно показать, но `live` выставляется только для нового успешного epoch. Для неизвестного времени последнего снимка/сообщения вернуть null. Детали используют оболочку `as_of`, `source`, `item`.

### Точные переходы здоровья (draft)

`starting` — до подключения, `syncing` — после подписки и до подтверждённой сверки плюс первого валидного non-retained push этого epoch. Такой push может прийти до REST и учитывается после commit. `last_mqtt_at` — локальное received_at такого сообщения, а не provider_time; дубликат тоже подтверждает доставку. После успешной сверки и push не старше 60 с — `live`. Если push ещё не было, отсчёт 60 с начинается от SUBACK; затем degraded и повтор подключения. При чтении heartbeat старше 15 с или last_mqtt_at старше 60 с переопределяет сохранённый live на degraded. Исторические отметки не подтверждают здоровье нового epoch. Таймауты используют монотонные часы, публикуемые даты — UTC.

Предлагаемые ограничения: 10 с на соединение и SUBACK, 5 с statement timeout БД, 15 с на весь bootstrap commit; превышение вызывает rollback и повторную сверку. Heartbeat обслуживает тот же писатель между транзакциями; временный degraded при затяжной операции допустим. Retry-After задаёт нижнюю границу ожидания, даже если превышает обычный предел backoff 60 с. Отдельное MQTT сообщение >64 КиБ отклоняется до разбора; лимит очереди считается по байтам payload, а не обещает потолок памяти Python. JSON имеет ограниченную глубину и число элементов; лимиты памяти процесса следует замерить.

## Операционные границы

Позиции доступны локально; backend не проксирует произвольные URL и не требует ключей в браузере. Сырой payload не сохраняется. Счётчики: валидные/отклонённые записи по причине, дубликаты, временные конфликты, размер очереди, возраст последнего MQTT, REST status, длительность запросов и рестарты. MMSI не помещаем в метки метрик. Запуск начинается с фиксированных синтетических данных; короткая проба реального источника — отдельный ручной smoke. Никаких заявлений о теневом флоте по результату одного сигнала.
